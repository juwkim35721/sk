# 도메인 유형별 클린 아키텍처 · 반도체·제조 6대 도메인 3-Step 알고리즘 · SVG 그래프 레퍼런스 (`ARCH_BLUEPRINTS.md`)

> **목적**: `7-plan`, `12-guide`, `13-doc`, `14-qa`에서 활용하는 클린 아키텍처, 반도체·제조 엔터프라이즈 6대 도메인 유형별 최적화 알고리즘 및 그래프 시각화 레퍼런스다.

## 1. 공통 웹 서비스 클린 아키텍처(Clean Architecture) 및 기술 선정 근거

### 1-1. 채택 아키텍처: 4-Layer Clean Architecture + SQLite 영속성 + Zero-Build Reactive SPA
- **Layer 1 — `Config & Persistence Infrastructure Layer` (`app/config.py`, `app/db.py`, `.env.example`, `Dockerfile`)**:
  - 모든 설정값과 비밀값(DB 접속 정보, 초기 계정 비밀번호, 포트 등)은 환경변수로 주입하며 코드 내 하드코딩을 금지한다.
  - 빈 DB에서 시작하더라도 스키마와 초기 시드 데이터가 자동 준비되며, 데이터셋과 생성 결과는 DB에 영속 저장되어 서비스 재시작 후에도 유지된다.
- **Layer 2 — `Dataset Validation & Repository Layer` (`app/data_loader.py`)**:
  - 전체화면 이탈을 유발하는 파일 업로드 창 없이, 서버에 준비된 데이터셋(원본, 정상 변경 데이터셋, 오류 주입 데이터셋)을 선택·검증·적용한다.
  - 필수 열 누락, 외래키(ID) 참조 무결성 위반, 형식/범위 오류를 실제 데이터 기반으로 검증하여 구체적 오류 사유를 반환하고, 검증 실패 시 트랜잭션을 롤백하여 기존 데이터와 생성 결과를 안전하게 유지한다.
- **Layer 3 — `Pure Domain & Optimization Engine Layer` (`app/core_engine.py`)**:
  - 웹 프레임워크나 DB 드라이버에 의존하지 않는 순수 도메인 계층으로, 하드 제약 불변식(용량 상한, 시간/납기, 예산, 스펙 한계, 비대상 제외 등)을 100% 준수하는 다단계 결정론적 최적화 알고리즘(최적화 라이브러리/솔버 또는 고속 휴리스틱)과 파라미터 재계산을 수행한다.
  - 극단적 파라미터 설정 등으로 제약을 만족할 수 없는 대상(실행 불가 조건)이 발생할 경우 조용히 누락하지 않고 `unassigned_warnings`로 명시적으로 보고한다.
- **Layer 4 — `Application Service, REST API & Dual-Role SPA Layer` (`app/simulator_api.py`, `app/main.py` + `app/static/*`)**:
  - 단일 포트(`0.0.0.0:8000`)에서 헬스체크(`/api/health`), 역할별 인증/접속(운영자 vs 구성원/검토자/교육생), 데이터셋 관리, 조건 변경 재계산, 부속 스키마 규격 JSON 내보내기 API와 프론트엔드 화면을 서빙한다.
  - **권한 및 개인정보 보호 (`require_admin_role` & `to_user_dto`)**: 운영자 API는 서버 핸들러에서 권한을 재확인하고, 일반 구성원 조회 API는 화면에서 숨기는 것이 아니라 서버 응답 DTO(`to_user_dto()`)에서 타인 정보와 민감 필드를 화이트리스트 방식으로 걸러내고 반환한다.
  - **상태 전이 무결성 및 화면 5대 상태**: 새로운 데이터셋 적용 후 재계산하기 전에는 이전 데이터셋의 결과를 새 데이터의 결과로 노출하지 않으며(`is_stale` 상태 관리), 프론트엔드는 **화면 상태 5종(`로딩 / 결과 없음 / 입력·검증 오류 / 재계산 필요(Stale) / 권한 없음`)**을 명확히 구분해 표시한다. 외부 CDN(`@import` 폰트/스크립트)은 절대 사용하지 않는다.

## 2. 반도체·제조 엔터프라이즈 6대 도메인 유형별 3-Step 알고리즘 · 그래프 시각화 · 대안 비교표

### 유형 A. 거점(노드) 선정 · 수요 배정 · 이동 경로/일정표 최적화
- **채택 3-Step 알고리즘 작동 원리**:
  1. **Step 1 (거점 노드 선정 — Demand-Weighted Greedy Set-Cover)**: 일자별 실제 대상 수요 지점(비대상 제외)의 좌표와 후보 거점 노드 간 거리를 계산하여, 허용 접근 반경 내 커버 수요가 많은 후보지부터 선정하고 원거리 소외 지점까지 모두 커버하도록 활성 거점 집합을 확정한다.
  2. **Step 2 (수요 배정 및 용량 분할 — Nearest Feasible Node Assignment)**: 각 일자·시간대별 수요를 가장 가까운 선정 거점 노드에 배정하고, 거점별 수요를 단위 용량 상한(Capacity Limit) 기준으로 분할·집계한다.
  3. **Step 3 (경로·경유순서·시간표 생성 — Savings 병합 + 용량/여유시간 제약 Greedy Insertion + 2-Opt)**: 구간별 소요시간 데이터와 도착 마감 시각, 출발 기준 시각, 최대 이동시간/경유수 기준을 만족하도록 거점 노드를 경로로 묶고, `2-Opt`로 경유 순서를 최적화하여 노드별 도착·출발 시각을 산출한다.
- **Native SVG 그래프 시각화 레시피**:
  - 외부 지도 API 없이 좌표를 캔버스 좌표계로 정규화하여 **거점·목적지를 노드(Node), 이동 구간과 소요시간을 방향 간선(Directed Edge)**으로 렌더링한다.
  - 구성원/현장 화면에서는 내 기준 위치 노드, 배정 거점, 다음 노드까지의 거리, 그리고 **현재 시각과 노드별 시간표를 선형 보간(Linear Interpolation)하여 계산한 현재 진행 위치 마커**를 그래프 위에 표시한다.
- **담당자 DM 핵심 확인 포인트**: 비활성 후보 거점 신규 활용 기준, 이용 편의 기준(수요 지점~거점 최대 허용 거리, 경로당 최대 소요시간 또는 최대 경유 노드 수).

### 유형 B. 구내식당 식단 편성 · 구성원 메뉴 선호 및 맞춤 추천
- **채택 3-Step 알고리즘 작동 원리**:
  1. **Step 1 (영양·예산·중복금지 제약 필터링 — Constraint Filtering)**: 일자·끼니별 목표 칼로리/단백질/나트륨 범위, 식단가 예산 상한, 조리설비/조리시간 한계, 그리고 최근 N일 내 동일 메뉴·주재료·조리법 연속 중복 금지 조건을 만족하는 유효 조합만 필터링한다.
  2. **Step 2 (구성원 선호도·잔반 저감 다중 가중치 편성 — Multi-Objective Greedy Scoring)**: 메뉴별 구성원 관심도/선호 점수와 과거 잔반율 역가중치, 영양 균형 점수를 합산해 일자별 최적 식단을 편성한다.
  3. **Step 3 (월간 예산·영양 평탄화 1-Swap 및 개인 맞춤 추천)**: 월간 총예산과 주간 영양 편차를 최소화하도록 인접 일자 간 메뉴를 교환(`1-Swap`)하고, 구성원 화면에서는 개인 알레르기 유발물질을 100% 제외한 뒤 선호 카테고리 기반으로 추천 메뉴를 산출한다.
- **Native SVG 그래프 시각화 레시피**:
  - 월간/주간 식단 편성 캘린더 매트릭스 + 메뉴-주재료-영양소-알레르기 연결 노드 그래프 및 일자별 칼로리·단가·선호도 달성률 추이 SVG 차트.
- **담당자 DM 핵심 확인 포인트**: 동일 메뉴/주재료 최소 재등장 간격(일수), 1식당 평균/최대 단가 기준, 특식일 운영 조건, 알레르기 및 구성원 선호도 반영 우선순위.

### 유형 C. 공정·지원 구역 안전 모니터링 센서/카메라 배치 및 사각지대 최소화
- **채택 3-Step 알고리즘 작동 원리**:
  1. **Step 1 (시야 가시영역 매핑 — FOV & Obstacle Ray-Casting)**: 공정 구역과 지원 구역의 좌표/그리드, 위험도 등급, 벽체/설비 장애물을 반영하여 후보 설치 위치·설치각별 실제 감시 가능 영역(Visibility Set)을 계산한다.
  2. **Step 2 (위험도 가중치 최대 커버리지 선정 — Risk-Weighted Greedy Set-Cover)**: 고위험 공정 구역 필수 감시(필요 시 교차 감시)와 총 설치 대수/예산 상한 제약 안에서 미감시 위험도 합계를 가장 크게 줄이는 위치·기종을 순차 선정한다.
  3. **Step 3 (사각지대 최소화 방위각/위치 로컬 보정 — Angle & Position Local Search)**: 잔여 사각지대(Blind Spot)를 줄이기 위해 인접 후보 위치 및 회전각을 미세 조정한다.
- **Native SVG 그래프 시각화 레시피**:
  - 공정·지원 구역 평면 노드/폴리곤 그래프 위에 센서/카메라 설치 노드, 시야각 부채꼴(FOV Sector), 감시 연결 간선, **커버 완료 구역(녹색) vs 사각지대 미커버 구역(적색 경고)**을 직관적으로 렌더링한다.
- **담당자 DM 핵심 확인 포인트**: 공정 구역과 지원 구역 간 최소 커버리지 기준 차이, 고위험 구역 중복(교차) 감시 필수 여부, 최대 설치 대수/예산 및 기존 설치분 이동 가능 여부.

### 유형 D. 반도체 노광/포토공정 품질(Overlay/계측) 진단 · 설비 배정 최적화
- **채택 3-Step 알고리즘 작동 원리**:
  1. **Step 1 (계측 오차 이상 진단 — Robust Z-Score & Rolling Drift)**: 로트·웨이퍼별 계측 데이터(dx, dy, 회전, 배율 오차 등)에서 중앙절대편차(MAD) 기반 `Robust Z-Score`와 시계열 이동평균 변화점(`Rolling Drift`)을 계산해 오차가 급증한 설비·척(Chuck)·레티클 조합을 식별한다.
  2. **Step 2 (스펙 한계 필터링 및 보정값 산출 — Spec Gate & APC Offset)**: 허용 품질 스펙(Spec Limit) 및 PM/인터락 기준을 초과한 위험 설비·척을 차단(또는 보정 Offset 산출)하고 투입 가능한 적격 설비군을 판별한다.
  3. **Step 3 (품질 마진·스루풋 균형 설비 배정 — Priority Dispatching + 1-Swap)**: 로트별 요구 정밀도와 납기 긴급도에 맞춰 최적 설비에 배정하고 `1-Swap`으로 설비 간 병목을 평탄화한다.
- **Native SVG 그래프 시각화 레시피**:
  - 웨이퍼 좌표별 계측 오차 벡터(화살표 크기·방향) SVG 맵 + `설비 <-> 척 <-> 레티클 <-> 공정 로트` 의존성 그래프 및 시계열 드리프트/스펙 상하한선 차트.
- **담당자 DM 핵심 확인 포인트**: 경고(Warning)와 투입 중단(Interlock/재작업)을 가르는 품질 허용 임계값, 척(Chuck) 편차 발생 시 단일 척 제외 운영 가능 여부, 품질 안정성과 설비 가동률 충돌 시 우선 기준.

### 유형 E. 반도체 원부자재 · 공급사 적격성 검토 및 물량 배분 최적화
- **채택 3-Step 알고리즘 작동 원리**:
  1. **Step 1 (품질 스펙 및 로트 산포 적격성 판정 — Qualification Gate)**: 후보 공급사별 테스트 로트의 순도, 불량률, 로트 간 편차(Cpk/일관성)를 현업 필수 기준과 대조하여 적격/조건부/부적격 공급사를 판별한다.
  2. **Step 2 (공급 리스크 분산 및 MOQ/Capa 제약 설정)**: 단일 공급사 의존도 상한(이원화 비율), 공급사별 최소발주량(MOQ), 최대 공급능력(Capa), 납기(Lead Time) 하드 제약을 설정한다.
  3. **Step 3 (품질·단가·리스크 다목적 물량 배분 — Constrained Utility Optimization)**: 필수 수요량을 100% 충족하면서 품질 리스크와 총조달 비용을 최소화하도록 공급사별 발주 물량과 전환 일정을 산출한다.
- **Native SVG 그래프 시각화 레시피**:
  - `공급사 -> 소재 -> 적용 공정/라인` 공급망 흐름 그래프 + 로트별 품질 산포 박스플롯/관리도 및 공급사별 리스크·단가·납기 레이더 비교 차트.
- **담당자 DM 핵심 확인 포인트**: 신규 공급사 승인 시 평균 품질과 로트 간 편차(안정성) 중 우선 기준, 기존 공급사 대비 최소 유지해야 할 안전 물량 비율, 납기 지연 허용 범위.

### 유형 F. 반도체 밸류체인 · 시장 실적 분석 및 도메인 학습 워크벤치
- **채택 3-Step 알고리즘 작동 원리**:
  1. **Step 1 (밸류체인 방향성 그래프 구축 및 시계열 정규화)**: 반도체 생태계(`IP/설계 -> 소재/장비 -> 웨이퍼/전공정 -> 패키징/후공정 -> 메모리/비메모리 제품 -> AI 서버/모바일 수요처`)를 방향성 그래프(DAG)로 모델링하고 기업·분기별 실적/출하량/ASP/재고 지표를 결합한다.
  2. **Step 2 (공급망 파급효과 및 시장 시나리오 시뮬레이션 — Graph Impact Propagation)**: 특정 수요처 성장률, 제품 가격(ASP), 설비투자(CapEx) 또는 공급 병목 파라미터 변경 시 연결된 상·하위 밸류체인 노드로 전파되는 실적·수급 영향도를 계산한다.
  3. **Step 3 (역할 맞춤형 이중 뷰 생성 — Business Analyst vs Domain Educator)**: 시장분석가 뷰에는 경쟁사 실적 비교·병목 노드·시나리오 손익 지표를 제공하고, 도메인 교육 뷰에는 선택 노드의 전후 공정 원리·핵심 용어·단계별 학습 경로를 생성한다.
- **Native SVG 그래프 시각화 레시피**:
  - 밸류체인 단계별 노드를 계층(Tier)별로 배치하고 거래/공정 의존성과 파급 강도를 간선 두께·색상으로 표현하는 인터랙티브 SVG DAG 그래프 + 분기별 경쟁사 실적·점유율 비교 차트.
- **담당자 DM 핵심 확인 포인트**: 시장분석 화면에서 중점 비교할 핵심 지표와 도메인 교육 화면에서 학습자에게 강조해야 할 밸류체인 연결 구조 및 난이도 기준.

### 공통: 대안 알고리즘 대비 채택 근거 요약표 (`12`번 실행·개발 명세서 기재용)

| 알고리즘 분류 | 장점 | 단점 | 채택 여부 및 이유 |
| :--- | :--- | :--- | :--- |
| **완전탐색 / 혼합정수계획법 (MILP)** | 소규모 고정 입력에서 수학적 전역 최적해 보장 | 데이터 규모 증가 시 연산 시간 급증으로 웹 화면 내 실시간 파라미터 재계산 불가 | 미채택 (실시간 조건 변경 재계산 및 응답성 불리) |
| **확률적 메타휴리스틱 (유전알고리즘 GA / SA)** | 복잡한 비선형 탐색 가능 | 실행 시마다 난수에 의해 결과가 달라져 검증 실행 시 결정론적 재현성(Determinism) 위배 | 미채택 (동일 데이터셋·조건 대비 일관된 검증 불가) |

## 4. 언어 · 프레임워크별 표준 코딩 컨벤션 (Google Style Guide & Clean Code)

모든 슬라이스 구현(`8`, `10`, `11`)과 검증(`9`)은 중구난방식 코딩을 금지하고 아래 언어·프레임워크별 표준 컨벤션을 엄격히 준수한다.

1. **Python (`Google Python Style Guide` & `PEP 8`)**:
   - **명명 규칙**: 함수·변수·모듈은 `snake_case`, 클래스·데이터모델은 `PascalCase`, 임계값·기본 정원 등 상수는 모듈 상단 `UPPER_SNAKE_CASE`로 정의하며 코드 내 매직 넘버(Magic Number) 하드코딩을 금지한다.
   - **타입 힌트 및 데이터 모델링**: 모든 핵심 함수 시그니처에 인자·반환 타입 힌트(`Type Annotations`)를 명시하고, 복잡한 중첩 딕셔너리 대신 `@dataclass`, `TypedDict`, 또는 `Pydantic BaseModel`을 사용한다.
   - **Docstring 및 함수 단일 책임**: 핵심 함수 상단에 1~3줄 Google Style Docstring(역할, 입출력, 핵심 수식/제약)을 작성하고, Early Return 패턴으로 중첩 조건문을 줄이며 함수당 하나의 책임만 부여한다.
   - **명시적 예외 처리 및 리소스 관리**: 에러를 숨기는 비특정 예외 처리(`bare except:`)를 절대 금지하고 구체적 예외와 오류 사유를 반환하며, 파일·DB 연결은 반드시 `with` 컨텍스트 매니저를 사용한다.
2. **FastAPI / Flask 백엔드 API (`Thin Router & RESTful Convention`)**:
   - **얇은 라우터 원칙 (Thin Controller)**: API 엔드포인트 함수(`simulator_api.py`) 내부에 알고리즘 연산이나 SQL 쿼리를 직접 작성하지 않고, 반드시 `data_loader.py`, `core_engine.py`, `db.py`의 함수를 호출만 한다.
   - **일관된 응답 및 에러 규격**: 정상 응답(`200`)과 입력 검증 실패 응답(`400`/`422`, 구체적 오류 사유 배열 포함)의 JSON 스키마를 통일한다.
3. **JavaScript / HTML / CSS (`Google JavaScript Style Guide` & `Modern ES6+`)**:
   - **모던 문법 및 명명 규칙**: `var` 사용을 금지하고 `const`(기본)와 `let`만 사용한다. 변수·함수는 `camelCase`, 상수는 `UPPER_SNAKE_CASE`를 사용한다.
   - **상태 · 통신 · 렌더링 분리**: 단일 상태 객체(`appState`)를 두고 비동기 API 통신 함수(`async/await` + `try/catch`), 그래프 좌표 정규화·보간 순수 계산 함수, DOM/SVG 렌더링 함수를 분리한다.
   - **스타일 일관성**: 인라인 스타일 남발을 피하고 `styles.css`의 `:root` CSS 변수(`Custom Properties`)로 색상·간격·상태 배지를 일관되게 관리한다.
4. **SQL / SQLite (`SQL Style Guide`)**:
   - SQL 키워드(`SELECT`, `INSERT`, `CREATE TABLE`, `WHERE`)는 대문자, 테이블·컬럼 식별자는 `snake_case`로 통일한다.
   - 문자열 포맷팅(`f"SELECT ... {x}"`) 쿼리 조합을 금지하고 100% 파라미터 바인딩(`?`)만 사용한다.

## 5. 운영 리스크 방어 및 6대 핵심 설계·트레이드오프 검증 포인트 표준 설계

코드 제출 후 진행되는 심층 기술 질의는 제출된 코드와 문서(`12`번 실행·개발 명세서, `13`번 기술 협업·검증 문서, `PLAN.md`)를 기반으로 진행된다. 따라서 핵심 엔지니어링 의사결정과 트레이드오프가 일관되게 설명되도록 아래 6대 포인트를 코드와 문서에 표준으로 반영한다.

| 핵심 설계·트레이드오프 영역 | 코드 내 표준 구현 (`8`번 스킬) | 문서 내 명시적 기록 (`12`번 실행·개발 명세서 한계점 섹션 / `13`번 협업·검증 문서) | 기술 질의 3단 답변 공식 (`구현 근거·한계 -> 파급 영향 -> 개선 계획`) |

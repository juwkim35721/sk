# 심층 기술 질의 대비 — 실제 코드(`app/*`) 구현 로직 명세 및 6대 설계·트레이드오프 복기 카드 (`sk/work/QA_CARD.md`)
> **생성 스킬**: `14-qa`
> **목적**: 코드 및 문서 제출 후 진행되는 심층 기술 질의에서 사용자가 구현 로직을 정확히 숙지하고, 코드와 제출 문서(`12`·`13`번 산출물)에 반영된 **6대 핵심 설계·트레이드오프 검증 포인트**에 대해 **`[1. 구현 위치·수식 및 한계 지목 -> 2. 파급 영향/이유 -> 3. 해결 방식 및 향후 개선 계획]` 3단 공식(250~400자)**으로 즉시 답할 수 있도록 한다.

## Part 0. 실제 코드(`app/*`) 기반 구현 로직 및 최적화 라이브러리 명세

### 1. 전체 클린 아키텍처 4계층 엔드투엔드 데이터 흐름도
- **[1단계: 화면 입력 및 5대 상태 관리 (`app/static/admin_view.js`, `user_view.js`)]**: 단일 상태 객체(`appState`)로 `로딩 / 결과 없음 / 오류 / 재계산 필요(Stale) / 권한 없음` 5대 상태를 관리하며, 운영자가 데이터셋 선택 또는 조건 변경 재계산 시 REST API(`app/simulator_api.py`)를 호출한다.
- **[2단계: 실제 검증 · 원자적 롤백 · 상태 차단 (`app/data_loader.py`, `app/db.py`)]**: 업로드 창 없이 서버 내 준비된 데이터셋(`data/datasets/*`)의 필수 열, 외래키(ID) 참조, 값 형식을 전수 검사한다. 오류 발견 시 상세 사유를 반환하고 기존 DB 확정본을 그대로 유지(롤백)하며, 통과 시 새 데이터를 저장하고 재계산 완료 전까지 이전 결과 노출을 차단(`is_stale`)한다.
- **[3단계: 최적화 라이브러리 / 3-Step 코어 엔진 (`app/core_engine.py`)]**: 순수 도메인 엔진이 근무일별 대상자를 필터링하고 `Step 1 -> Step 2 -> Step 3` 최적화 알고리즘(및 최적화 라이브러리/솔버)을 수행해 하드 제약을 100% 만족하는 결과를 산출한다. 제약 충족이 불가능한 예외 대상은 조용히 누락하지 않고 `unassigned_warnings`로 명시적 경고를 반환한다.
- **[4단계: 권한 분리 · 화이트리스트 DTO · 그래프 시각화 (`app/simulator_api.py`, `app/static/*`)]**: 운영자 API는 서버에서 `require_admin_role()`로 권한을 재확인하고, 구성원 조회 API는 `to_user_dto()` 화이트리스트로 타인 정보·민감 필드를 서버에서 제거한 뒤 반환한다. 화면에서는 외부 지도/CDN 없이 좌표 정규화 및 시간표 선형 보간으로 노드 그래프와 현재 위치를 렌더링한다.

- **핵심 키워드 및 코드 근거**: `app/core_engine.py`의 `...` 함수, 사용한 라이브러리/솔버 `...`, 임계값 `...`
- **3단 구조 실전 답변 문단 (250~400자)**:
  > **[구현 및 근거]** `app/core_engine.py`의 `...()`에서 ... (Step 1 거점 선정 -> Step 2 배정/분할 -> Step 3 경로·시간표 산출 및 사용한 라이브러리/수식 설명). 실시간 재계산 응답성(...ms 이내)과 동일 입력 대비 100% 결정론적 재현성을 보장하기 위해 이 방식을 채택했습니다.
  > **[한계 및 파급 영향]** 다만 ... 단계에서 그리디/로컬 탐색 특성상 교차 권역 수요가 급증하거나 제약이 극단적일 때 전역 최적해 대비 1~2대의 추가 차량(리소스)이 투입되는 국소 최적해 한계가 있습니다.

### 문항 2 (주제 2: 운영 장애 · 다수 관리자 동시 수정/재계산 충돌 및 DB 영속성)
- **예상 질문**: "여러 운영자가 동시에 데이터셋을 변경하거나 재계산을 실행할 때, 또는 사용자가 조회하는 도중 서버 장애나 재계산이 발생하면 어떻게 동작하며 어떻게 개선할 것인가?"
- **핵심 키워드 및 코드 근거**: `app/db.py`의 `...`, `is_stale` 플래그, 동시 수정 여부 확인에 따른 설계 판단 및 `version` 낙관적 잠금(`409 Conflict`)
- **3단 구조 실전 답변 문단 (250~400자)**:
  > **[구현 및 가정]** 데이터와 결과는 `app/db.py`의 SQLite 테이블(`...`)에 트랜잭션으로 영속 저장해 재시작 후에도 유지되며, 데이터셋 변경 직후 `is_stale` 상태를 설정해 재계산 완료 전까지 이전 결과가 새 결과로 노출되지 않도록 막았습니다. (현업 담당자 확인 결과 동시 수정 요구가 없어 과잉 구현을 피하고자 별도 동시 잠금은 생략했습니다 / 또는 요구에 따라 잠금을 반영했습니다.)
  > **[한계 및 파급 영향]** 다만 다수 운영자가 동시에 무거운 재계산이나 데이터셋 적용을 요청하는 환경으로 확장될 경우, 단일 SQLite 쓰기 잠금(`database is locked`) 대기나 마지막 요청 덮어쓰기(Lost Update) 위험이 있습니다.
  > **[향후 개선 계획]** 이를 해결하기 위해 `db.py`의 설정·데이터셋 테이블에 `version` 컬럼을 두어 `UPDATE ... WHERE version=?` 실패 시 `409 Conflict`와 충돌 안내창을 띄우는 낙관적 잠금과 단일 활성 재계산 작업 잠금(Job Lock)을 도입하고, 조회는 게시된 확정 스냅샷을 읽도록 분리하겠습니다.

### 문항 3 (주제 3: 운영자/구성원 권한 분리 및 개인정보 화이트리스트 DTO 보안)
- **예상 질문**: "운영자와 구성원의 권한 및 책임을 어떻게 분리했으며, 구성원 조회 시 타인의 개인정보나 관리자 전용 데이터가 노출되지 않도록 어떻게 방어했는가?"
- **핵심 키워드 및 코드 근거**: `app/simulator_api.py`의 `require_admin_role()`, `to_user_dto()`
- **3단 구조 실전 답변 문단 (250~400자)**:
  > **[구현 및 방어]** 프론트엔드 화면 탭만 분리하면 API 직접 호출 시 권한 우회 및 타인 정보 유출 위험이 있습니다. 이를 막기 위해 `app/simulator_api.py`에서 데이터셋 적용·조건 변경·재계산 엔드포인트는 핸들러 내부의 `require_admin_role()`을 통해 서버 측 권한을 강제 검증했습니다.
  > **[개인정보 화이트리스트]** 또한 구성원 조회 API는 DB 원본 행을 그대로 반환하지 않고 `to_user_dto()` 화이트리스트 변환 함수를 거쳐 타 구성원의 식별자·개인 좌표·부서 등 민감 필드를 서버에서 원천 제거한 뒤 본인 배정 결과·일정표·구간 거리·현재 진행 위치 정보만 반환하도록 구현했습니다.
  > **[향후 개선 계획]** 향후 운영 환경에서는 서명된 세션 토큰 만료 정책과 역할별 감사 로그(Audit Log)를 `db.py`에 추가해 접근 통제를 한층 강화하겠습니다.

### 문항 4 (주제 4: 잘못된 데이터셋 원자적 롤백 및 실행 불가 조건 경고 처리)
- **예상 질문**: "잘못된 입력 데이터셋이 들어오거나, 운영자가 설정한 파라미터로 제약 조건을 만족할 수 없는 예외 상황에서는 어떻게 처리했는가?"
- **핵심 키워드 및 코드 근거**: `app/data_loader.py`의 `validate_dataset()`, `app/core_engine.py`의 `unassigned_warnings`
